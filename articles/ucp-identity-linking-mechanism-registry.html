UCP Identity Linking Redesigned with Mechanism Registry

A significant architectural overhaul transforms UCP's identity linking from a hardcoded OAuth 2.0 implementation into an extensible, security-hardened system built on mechanism registries and capability-driven scope derivation.

About the Author

Amit Handa (@amithanda) is a contributor to UCP focused on identity and authentication systems. This PR represents a major evolution of the protocol's approach to merchant-platform identity linking.

Why This Matters

Identity linking is how AI shopping agents establish authenticated sessions with merchants on behalf of users. The original UCP specification hardcoded OAuth 2.0 as the only mechanism, creating two problems:

  • Limited extensibility: Adding support for verifiable credentials, passkeys, or other authentication mechanisms would require breaking changes
  • Over-permissioning risk: Scopes were declared separately from capabilities, making it possible for implementations to request more permissions than needed

This PR solves both problems with an elegant abstraction that mirrors TLS cipher suite negotiation.

What Changed

Mechanism Registry Pattern

Businesses now declare an ordered array of supported authentication mechanisms:

{
  "supported_mechanisms": [
    {
      "type": "oauth2",
      "client_id": "ucp-agent-xyz",
      "authorization_endpoint": "https://merchant.example/oauth/authorize"
    },
    {
      "type": "verifiable_credential",
      "accepted_issuers": ["did:web:identity.example"]
    }
  ]
}

Platforms select the first mechanism they support, with business preference ordering. This mirrors how TLS negotiates cipher suites — the server lists preferences, the client picks the first one it can handle.

A formal Mechanism Selection Algorithm is now defined: iterate from index 0, select the first type the platform supports, abort if none match. No fallback flows permitted.

Capability-Driven Scope Derivation

Authorization scopes are no longer declared in identity linking config. Instead, each capability schema declares its own required scopes:

// checkout.json
{
  "$id": "dev.ucp.shopping.checkout",
  "identity_scopes": "dev.ucp.shopping.scopes.checkout_session",
  // ...
}

Scopes are derived only from the finalized capability intersection. If a capability gets excluded during negotiation, its scopes contribute nothing. This makes over-permissioning impossible by construction, not convention.

The capability intersection algorithm gains two new steps:

  1. Step 3 — Scope Dependency Pruning: Capabilities declaring identity_scopes are removed if identity linking isn't in the intersection
  2. Step 5 — Derive Scopes (Final Pass): Authorization scope set computed from stabilized intersection only

Hardened OAuth 2.0 Security

The OAuth 2.0 mechanism requirements align with current best practices:

Requirement Before After
PKCE (RFC 7636) Not required MUST use S256
iss validation (RFC 9207) Not mentioned MUST validate (Mix-Up Attack prevention)
redirect_uri matching Not mentioned MUST exact string match
Issuer normalization Not mentioned MUST strip trailing slashes

Scope Naming Convention

Scopes now use reverse DNS dot notation with a mandatory .scopes. segment:

  • UCP-defined: dev.ucp.<domain>.scopes.<capability>
  • Third-party: <reverse-dns>.scopes.<capability>

Example: dev.ucp.shopping.scopes.checkout_session

Implications for Implementers

Merchants

Update capability configs to use the new supported_mechanisms array format. Existing OAuth 2.0 configs will need migration. The new format allows adding future authentication methods without protocol changes.

Platforms (AI Agents)

Implement the mechanism selection algorithm and update scope handling to derive from capability intersection. PKCE support is now mandatory for OAuth 2.0 flows.

Extension Authors

Capabilities requiring authenticated sessions should declare identity_scopes in their schema following the reverse DNS convention.

Next Steps

This architecture enables several future enhancements:

  • Verifiable Credentials: A verifiable_credential mechanism type for W3C VC-based authentication
  • Passkeys/WebAuthn: Direct FIDO2 authentication without OAuth
  • Delegated Identity: Mechanisms for multi-hop agent delegation chains
