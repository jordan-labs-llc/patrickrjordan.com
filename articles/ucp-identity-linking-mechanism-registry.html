UCP Identity Linking Redesign: Mechanism Registry Pattern

A major architectural change that transforms UCP's identity linking from hardcoded OAuth 2.0 to an extensible, security-hardened mechanism registry — enabling future authentication methods without protocol changes.

About the Author

Amit Handa is a contributor to the Universal Commerce Protocol. This PR represents one of the more significant architectural changes to UCP's authentication layer since the protocol's inception, moving from a fixed OAuth 2.0 implementation to a flexible mechanism registry pattern.

Why This Matters

Identity linking is the bridge between AI agents and user accounts on merchant systems. When you ask an AI shopping assistant to "check my order status" or "apply my loyalty points," the agent needs secure, authenticated access to your merchant account. Previously, UCP hardcoded OAuth 2.0 as the only authentication mechanism.

This works today, but what about:

  • Verifiable Credentials — W3C's emerging standard for portable digital identity
  • Passkeys / WebAuthn — Passwordless authentication gaining rapid adoption
  • Decentralized identifiers (DIDs) — Self-sovereign identity systems

The mechanism registry pattern solves this by making authentication methods pluggable. Businesses declare what they support; platforms select the first method they understand. No protocol changes needed when new authentication methods emerge.

What Changed Technically

1. Mechanism Registry Pattern

Instead of assuming OAuth 2.0, businesses now declare their supported mechanisms in order of preference:

{
  "supported_mechanisms": [
    {
      "type": "oauth2",
      "authorization_server": "https://auth.example.com",
      "client_id": "ucp-platform-abc"
    },
    {
      "type": "verifiable_credential",
      "issuer": "did:web:example.com",
      "proof_types": ["jwt_vc"]
    }
  ]
}

The selection algorithm mirrors TLS cipher suite negotiation: iterate from index 0 (highest preference), select the first type both parties support, abort if none match. No partial or fallback flows permitted — this eliminates downgrade attacks.

2. Capability-Driven Scope Derivation

Previously, OAuth scopes were hardcoded or pre-declared. Now scopes emerge from capability intersection:

  • Each capability schema declares its required scopes via an identity_scopes annotation
  • Scopes derive only from finalized capability intersection — excluded capabilities contribute zero scopes
  • If a capability requires identity but identity linking isn't in the intersection, that capability is pruned

This makes over-permissioning impossible by construction, not convention. An agent can never request more access than the active capability set requires.

3. Hardened OAuth 2.0 Security

The OAuth 2.0 mechanism requirements are significantly tightened:

Requirement Before After
PKCE (RFC 7636) Not required MUST use S256
iss validation (RFC 9207) Not mentioned MUST validate (prevents Mix-Up Attacks)
redirect_uri matching Not mentioned MUST enforce exact string match
Discovery error handling Unspecified Only HTTP 404 triggers OIDC fallback; 5xx/timeouts abort

4. Scope Naming Convention

Scopes now use reverse DNS dot notation with a mandatory .scopes. segment:

  • UCP-defined: dev.ucp.shopping.scopes.checkout_session
  • Third-party: com.example.loyalty.scopes.points_balance

A regex pattern in the schema enforces this convention, preventing ambiguous or conflicting scope names.

Next Steps & Implications

Breaking Change

This is a breaking change to the protocol. Existing integrations using hardcoded OAuth 2.0 will need to migrate to the new supported_mechanisms format. The enhanced security requirements (mandatory PKCE, iss validation) may also require updates to authorization server implementations.

For UCP implementers:

  • Update capability negotiation to include scope derivation (new Step 5)
  • Implement mechanism selection algorithm on the platform side
  • Ensure OAuth 2.0 implementations meet hardened requirements

For the ecosystem:

  • Watch for verifiable credential mechanism proposals — the registry pattern explicitly invites them
  • Expect similar patterns to emerge in A2A for agent-to-agent identity federation
  • The capability-driven scope derivation pattern could influence MCP's evolving permission model
