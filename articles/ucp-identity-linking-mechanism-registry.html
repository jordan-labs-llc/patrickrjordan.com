UCP Identity Linking Mechanism Registry Merges: Extensible Authentication Arrives

A breaking change redesigns how AI agents prove user identity to merchants — replacing hardcoded OAuth providers with a discoverable, extensible mechanism registry. Essential infrastructure for enterprise compliance and future authentication methods.

Author: Amit Handa

UCP contributor focused on identity and authorization flows. Previously contributed to payment authentication specs.

Why This Matters

When an AI agent wants to buy something on behalf of a user, it needs to prove who that user is. The previous UCP identity model assumed OAuth-style providers (Google, Apple, etc.) with hardcoded discovery. This works for consumer scenarios but breaks down in enterprise environments where:

  • Custom identity providers — Enterprises use SAML, Active Directory, or proprietary SSO systems
  • Regulated industries — Financial services and healthcare require specific authentication methods
  • Wallet-based identity — Crypto wallets and verifiable credentials need first-class support
  • Regional requirements — Different markets have different identity verification standards

The new mechanism registry pattern makes identity providers pluggable. Platforms declare supported mechanisms, businesses state requirements, and agents negotiate compatible authentication flows at runtime.

What Changed Technically

The PR introduces three key concepts:

1. Mechanism Registry

A standard registry of authentication mechanism types. Each mechanism declares its contract: what inputs it requires, what claims it produces, and how verification works.

{
  "identity_mechanisms": {
    "oidc": {
      "type": "oidc",
      "issuers": ["https://accounts.google.com", "https://appleid.apple.com"]
    },
    "wallet_attestation": {
      "type": "wallet_attestation",
      "chains": ["ethereum", "solana"],
      "attestation_types": ["ownership", "balance"]
    },
    "enterprise_sso": {
      "type": "saml",
      "metadata_url": "https://company.example/.well-known/saml-metadata"
    }
  }
}

2. Capability-Driven Scopes

Mechanisms declare what claims they can provide, and operations declare what claims they require. The platform matches them automatically:

// Checkout operation might require:
{
  "required_claims": ["email", "shipping_address"],
  "optional_claims": ["phone", "loyalty_id"]
}

// An OIDC mechanism provides:
{
  "available_claims": ["email", "name", "phone"]
}

3. Link Delegation Extension

For agents acting on behalf of users across contexts, the link_delegation extension (PR #247, also merged this week) enables secure credential handoff without exposing raw tokens.

Breaking Change Impact: Existing identity linking implementations that hardcode OAuth discovery will need to migrate to the registry pattern. The spec includes a transition period where both patterns work, but the hardcoded approach is deprecated.

The Wallet Attestation Follow-Up

Just hours after the mechanism registry merged, PR #280 landed adding wallet_attestation as the first new mechanism type. This enables:

  • Proof of wallet ownership — Cryptographic proof that a user controls a specific wallet address
  • Balance attestations — Verified claims about on-chain holdings without exposing exact amounts
  • NFT-gated commerce — Merchants can require specific token ownership for purchases

This is the extensibility model working as designed — a new authentication method added without changing the core protocol.

Implications

For platform implementers: Update identity handling to use the registry pattern. Start with OIDC for compatibility, then add mechanisms as business needs arise.

For merchants: The new model enables requiring specific authentication strength (e.g., "must use enterprise SSO" for B2B transactions) without custom integration work.

For the ecosystem: This is UCP maturing from "works for Google Shopping" to "works for enterprise commerce." The mechanism registry pattern is the kind of extensibility infrastructure that enables long-term protocol growth.
